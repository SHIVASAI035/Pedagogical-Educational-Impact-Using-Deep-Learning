# Dataset Description

## 1. What data the project uses

The project uses **two separate, clearly synthetic data sources**:

| Source | Purpose | Where it lives |
|---|---|---|
| Student-performance dataset | Train and evaluate the TensorFlow/Keras ANN | `backend/app/dataset/student_performance.csv` |
| Demonstration cohort | Populate the MySQL database so every dashboard has realistic records | Created by `backend/app/seed_data.py` |

> **Important:** Neither source contains real students, real teachers or real
> institutions. No public dataset was copied. All values are generated by the
> documented processes below. The project must not present these numbers as
> evidence about real teaching or real learners.

## 2. Why a synthetic dataset was necessary

The specification requires seven specific model inputs:

1. Attendance percentage
2. Daily study hours
3. Previous examination marks
4. Assignment completion percentage
5. Class participation
6. Learning engagement
7. Subject-wise performance

Public educational datasets do not contain this exact combination. For example,
the widely used UCI *Student Performance* dataset (Cortez & Silva, 2008) has
grades, absences and demographic/behavioural survey items, but it does **not**
contain assignment completion, classroom participation or engagement
observations. Deriving those columns and then presenting the result as a public
dataset would be fabrication.

A synthetic dataset with an explicit, reproducible data-generating process (DGP)
is therefore the honest choice. Every limitation of that choice is reported in
Section 8 and in `docs/PROJECT_REPORT.md`.

## 3. Model dataset: schema

File: `backend/app/dataset/student_performance.csv`
Metadata: `backend/app/dataset/student_performance.meta.json`

| Column | Unit / range | Description |
|---|---|---|
| `attendance_pct` | 45–100 | Percentage of scheduled classes attended |
| `study_hours` | 0.5–9.0 | Self-reported focused study hours per day |
| `previous_marks` | 25–98 | Previous examination percentage |
| `assignment_completion` | 25–100 | Percentage of assignments completed |
| `class_participation` | 15–100 | Observed class participation |
| `learning_engagement` | 5–100 | Composite engagement indicator |
| `subject_performance` | 10–100 | Subject-wise performance average |
| `final_score` | 0–100 | **Target**: academic score |

- Rows: **4,000**
- Features: **7**
- Target: **1**
- Random seed: **42** (reproducible)
- Missing values: approximately **1.5% per feature** (about 413 cells total),
  injected so that median imputation is exercised by real missingness.

## 4. Data-generating process (DGP)

All features are drawn from normal distributions and clipped to plausible
educational ranges:

```
attendance_pct        ~ Normal(84, 9)        clipped [45, 100]
study_hours           ~ Normal(3.2, 1.25)    clipped [0.5, 9]
previous_marks        ~ Normal(67, 12)       clipped [25, 98]
assignment_completion ~ Normal(79, 13)       clipped [25, 100]
class_participation   ~ Normal(68, 14)       clipped [15, 100]

learning_engagement   = 0.55*participation + 0.35*attendance - 18 + N(0, 6)
subject_performance   = 0.60*previous_marks + 0.25*engagement + 10 + N(0, 6)

final_score =
      0.22*previous_marks
    + 0.16*subject_performance
    + 0.18*attendance_pct
    + 0.10*(study_hours/9*100)
    + 0.14*assignment_completion
    + 0.08*class_participation
    + 0.12*learning_engagement
    + 6.0*(engagement/100)*(attendance/100)     # small interaction term
    - 8.0*max(0, 65-attendance)/65              # attendance penalty
    + N(0, 4.2)                                 # irreducible noise
clipped to [0, 100]
```

The DGP is implemented in `backend/app/dataset/generate_dataset.py` and can be
re-run at any time:

```powershell
cd backend
.venv\Scripts\python.exe -m app.dataset.generate_dataset --rows 4000 --seed 42
```

Regenerating with the same `--rows` and `--seed` reproduces the same file. The
admin UI exposes the same operation at **Model performance → Dataset
management** (`POST /api/admin/dataset/regenerate`).

## 5. Preprocessing

The pipeline is fitted **only on the training partition** to avoid leakage:

1. 70% train / 15% validation / 15% test split (`random_state=42`).
2. `SimpleImputer(strategy="median")` fitted on training rows.
3. `StandardScaler` fitted on the imputed training rows.
4. The same fitted objects transform validation and test rows.
5. Imputer and scaler are serialised with `joblib`:
   `imputer.pkl`, `scaler.pkl`.

Resulting split sizes: **2,800 train / 600 validation / 600 test**.

## 6. Demonstration cohort (database seed)

`backend/app/seed_data.py` creates a synthetic institution:

- 1 administrator, 6 teachers, 54 students
- 3 classes (Grade 9-A, Grade 9-B, Grade 10-A), 15 subjects
- 60 days of attendance, 12 weeks of learning activity
- 2 assignments per subject with submissions
- 4 exams per student per subject
- 6 teaching sessions and 6 classroom observations per teacher
- 3 feedback responses per student (162 total)

Each student is given latent propensities (ability, attendance, engagement,
study hours, participation, completion) that drive the generated records. A
**modest association** between methodology and outcomes is deliberately planted
so the comparison screens are not empty:

```python
METHOD_EFFECT = {
    "Lecture": 0.0,
    "Demonstration": 1.8,
    "Collaborative Learning": 2.6,
    "Flipped Classroom": 2.1,
    "Project Based Learning": 3.0,
    "Discussion": 2.2,
}
```

This planted effect is **a property of the simulation, not evidence**. The
impact module and UI state this explicitly: differences between methodologies
are associations, and the data were not collected through a randomised or
controlled design.

## 7. Evaluation protocol

- The ANN is trained on the training split with early stopping on validation
  loss (`patience=20`, `restore_best_weights=True`).
- MAE, MSE, RMSE and R² are computed on the **held-out test split** that the
  model never saw during training or early stopping.
- The values shown in the UI are read from
  `backend/app/deep_learning/artifacts/metrics.json`, produced by the actual
  training run. Nothing is hard-coded.
- A fresh training run may produce slightly different values because of
  floating-point non-determinism, even with a fixed seed.

## 8. Limitations

1. **Synthetic data.** The model learns the DGP above, not real learning
   behaviour. Its metrics measure how well the ANN recovers that DGP.
2. **Self-report bias.** Study hours and engagement would be self-reported in a
   real deployment.
3. **No causal identification.** The cohort is observational. No teaching method
   can be said to cause an outcome.
4. **Simplified construct.** "Teacher quality" and "engagement" are latent
   simulation parameters, not validated psychometric instruments.
5. **Class composition not controlled.** Methodology is confounded with teacher,
   subject difficulty and class.
6. **Small demonstration cohort.** 54 students is enough to demonstrate the
   application, not to support generalisable conclusions.
7. **Feedback text is templated.** NLP results demonstrate the pipeline; they do
   not measure real student sentiment.

## 9. Ethical and privacy notes

- All names, emails, roll numbers and comments are fictional.
- Feedback summaries never expose student identity; only aggregate statistics
  and anonymised comments are returned by the API.
- Predictions are presented as a **support signal**, never as a final academic
  judgement.
- The application must not be deployed with these demo credentials or this
  synthetic data in a real institution without replacing both.
